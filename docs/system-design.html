01Problem & goals

AMP customers hold per-vehicle monthly wash subscriptions, buy single washes, and keep a payment method on file. When something goes wrong they call a CSR. The portal is built around the four calls CSRs actually take:

  1. "I want to cancel my account." — one action that atomically cancels the account and every live subscription.
  2. "I have a question about a recent purchase." — full, paginated purchase history with statuses and failure reasons.
  3. "I purchased a new vehicle and I want my subscription transferred." — the flagship flow: move a membership between the caller's vehicles with an audit trail.
  4. "I am not able to get a wash." — the account is OVERDUE after a failed payment; the portal must say so immediately, with the reason.

Design goals that follow: speed to answer (everything about a customer on one scannable page), correctness under concurrency (two CSRs can work the same account), and auditability (transfers leave a permanent record).

02Architecture

One Next.js app, one deploy. The back-end is Route Handlers acting as thin controllers over a controller → service → repository layering. Each layer has one job and one dependency direction:

Why this shape

  • Testability — business rules (the transfer invariants, the overdue-clearing rule) are plain functions over injected fakes.
  • Blast-radius control — Prisma is confined to one layer; HTTP is confined to another. Swapping either touches one directory.
  • One schema, both sides — src/lib/schemas/ zod schemas are parsed by the API and used as form resolvers, so client and server can't drift.

04Data model

Six models, four enums. The two deliberate moves: Subscription.vehicleId is mutable (a transfer is an in-place pointer update, so plan and billing history survive), and SubscriptionTransfer is an append-only audit table written in the same transaction.

Overdue modeling. OVERDUE is not free-floating state: it's caused by a FAILED SUBSCRIPTION_PAYMENT purchase carrying a human-readable failureReason. The user-detail endpoint includes the latest FAILED purchase so the banner ("payment failed on {date}: {reason}") renders in one round trip. Cancelling a user's last OVERDUE subscription flips the account back to ACTIVE in the same transaction.

07Frontend design

Client-side React Query against the API — the right default for an interactive internal tool (search-as-you-type, dialog mutations, cache invalidation); server components are thin shells.

  • /users — DataGrid in full server mode (pagination, sorting), 300 ms debounced search, status filter. All list state lives in the URL, so views are shareable and back/refresh-safe. keepPreviousData keeps paging smooth.
  • /users/[id] — stacked scannable cards rather than tabs: a CSR on a call needs everything visible. Header (status chip, Cancel Account), OVERDUE banner, account card + edit dialog, subscriptions (add / cancel / transfer + history), vehicles, purchases.
  • Cache strategy — two key families: ['users', params] (list) and ['user', id] (detail) + ['purchases', id, page]. Every mutation invalidates ['user', id] and ['users'], because account status (ACTIVE/OVERDUE) derives from subscriptions — the list chip must update too.
  • Forms — react-hook-form with the same zod schemas the API parses. Server fieldErrors map back via setError under the exact input; non-field errors go to a dialog Alert or snackbar. Buttons disable while mutations are pending.
  • Failure states — every section has a skeleton, an empty state, and an Alert-with-retry; route-level error.tsx and not-found.tsx catch the rest.

08CI/CD & deployment

  • Connection strings — the app uses Neon's pooled string (serverless-friendly); migrations use the direct string.
  • Prisma on Vercel — "postinstall": "prisma generate" defends against Vercel's node_modules caching serving a stale client.
  • Deliberate cut — preview deploys share the prod database; acceptable for a take-home and documented.

09Testing strategy

39 unit tests (Vitest), zero database. Services are factory functions taking repositories and runInTransaction as parameters, so tests pass hand-rolled fakes and assert on business behavior, not SQL:

  • subscription.service.test.ts — the flagship: transfer happy path (asserts the vehicleId update and the audit insert happen in the same tx), target-already-subscribed 409, cross-owner 400, cancelled-sub 409, and cancel-clears-user-OVERDUE.
  • user.service.test.ts — duplicate-email conflict (including the P2002 race backstop), cancel cascade, not-found, list param passthrough.
  • vehicle.service.test.ts — duplicate plate, delete-with-live-sub 409.
  • api-helpers.test.ts — the error → status envelope mapping.

Above unit level: CI runs typecheck + build on every PR, the post-deploy smoke check exercises the live API, and the README's demo walkthrough doubles as a manual e2e script mapped to the four call scenarios. A Playwright suite is the next investment (§10).
